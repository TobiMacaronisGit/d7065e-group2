# Design decisions

Report section 4.4 — the table that carries most of the architecture grade. Pattern (report guide §2.6):
**"X was chosen because … (requirement); the alternative was Y; the trade-off accepted is Z."**
A row without a rejected alternative is an assumption, not a decision.

| # | Decision | Chosen | Alternatives considered | Justification (requirement) | Trade-off accepted |
|---|---|---|---|---|---|
| D-01 | Implementation language | Python 3.12 for all our services | **Go** (course recommendation, single 6 MB static binary, BuildSim itself is Go); Rust | Neither of us knows Go; with ~6 weeks the risk of learning a language *and* a distributed architecture is concentrated in the same weeks. The numeric and data stack we need (numpy for the regression, DuckDB for Parquet) is native in Python. | ~150 MB images instead of ~6 MB, slower start-up, more RAM for ~25 containers. **We measure image size, RSS and start-up time and report them** — this is the one decision where we knowingly went against the recommendation, so it needs evidence, not an excuse. |
| D-02 | Inter-service transport | **MQTT** (Mosquitto), QoS 1, persistent sessions, retained commands/states/plans | Direct REST between services; Kafka; Redis streams | Four independent consumers need the same readings (`control`, `planner` via pipeline, `pipeline`, `viewer`); pub/sub decouples them so a consumer can restart without disturbing sensors (NFR-02). Retained messages let a restarted actuator recover its last command without asking anyone. Kafka brings partitions, brokers and ZK/KRaft we would not use. | One more process to run and monitor; at-least-once delivery means consumers must be idempotent (applying an actuator command is, by construction). |
| D-03 | Historical storage | `pipeline` container: **bronze JSONL → silver Parquet via DuckDB**, plus an HTTP query API | InfluxDB; TimescaleDB (the worked example's choice); Prometheus (what the professor demoed) | The pipeline must serve three different readers — dashboard, planner training, evaluation — and files are the most transparent way to do that at lab scale: inspectable, replayable, no server. Prometheus is pull-based and lossy by design (it scrapes), which makes it wrong as the raw store for model training. | No native Grafana datasource → Grafana reads JSON through the Infinity plugin; no retention/compaction beyond our own `compact()`. |
| D-04 | Dashboard | **BuildSim overlays** (room layers + alerts) via one `viewer` container **+ Grafana** | A hand-written web dashboard; BuildSim overlays only | The 3D viewer is provided infrastructure — the honest move is to map our state into it and say so, not to claim it as our component. Grafana gives time series with zero UI code of ours. | Two places to look; Grafana panels depend on the Infinity plugin being installable offline. |
| D-05 | Device granularity | **One container per physical device** (10 sensors + 10 actuators), Compose generated from `config/rooms.json` | One gateway container per room; one container per signal type | Each real device has its own fault domain: the "CO₂ sensor freezes while everything else keeps running" scenario is only honest if that sensor really is its own process (NFR-02, NFR-05). | ~25 containers on one laptop; the Compose file must be generated to stay in sync with the config; resource ceiling reached sooner (which we turn into the boundary-testing experiment). |
| D-06 | Occupancy source | Read `GET /api/occupancy` from **BuildSim**, published there by occupancysim | Poll occupancysim's own API directly; write our own occupancy model | Keeps BuildSim as the only shared state and makes occupancy just another sensor stream, so the pipeline and the forecast treat it uniformly. Writing our own people model would duplicate a course tool for no grade. | We inherit occupancysim's assumptions (room roles by area, deterministic day plans) and must state them. |
| D-07 | Forecast method | **Linear regression on lagged occupancy + time-of-day**, then a deterministic CO₂ rollout | Rolling the physics forward with current occupancy (no forecast); an ML classifier; an LLM agent | The genuinely uncertain quantity is *future occupancy*; once that is predicted, the CO₂ trajectory is a deterministic consequence of equations we already have. A rollout without an occupancy forecast is circular (it assumes what it should predict). LR is transparent, trains in seconds, and has an obvious baseline to beat. | Cannot represent sudden regime changes; deliberately evaluated against a persistence baseline so a "no better than trivial" result is visible rather than hidden. |
| D-08 | Decision architecture | Reactive rules + hard safety clamp (`control`), advisory planner that may **only raise** | One controller that does both; MPC optimiser | The safety-relevant function stays simple enough to verify and explain from memory (oral exam); the advisory-only interface means a wrong or absent plan degrades the system to "reactive", never to unsafe (REG-01). | Less optimal than a true optimiser; the planner cannot save energy by lowering ventilation below what the rules demand. |
| D-09 | Command authority | `control` publishes commands; the **actuator process** validates issuer, range, freshness and applies at a rate limit | `control` writes `PUT /api/actuators/{id}/state` to BuildSim directly | Required by the lab quickstart ("proposing a command is not the same as validating and applying it"), and it is what makes SAF-01 testable at all — there is a component whose job is to say no. | One more hop and one more process per actuator; a rejected command is only visible in logs/metrics, so we expose a `rejected` counter. |
| D-10 | Time authority | occupancysim's clock via `GET /api/state`; every message carries `ts` (wall) **and** `sim_ts` | Each service keeps its own accelerated clock; use wall time only | Time-sync between a 60× simulated clock and the physics timestep was our biggest flagged risk; one authority removes the class of bug entirely. Dwell times and windows are specified in sim-time, latency in wall-time. | If occupancysim is unreachable, clocks extrapolate and drift — so services report `clock_degraded` rather than pretending. |
| D-11 | Room selection | A109, A117 (lecture), A110 (fika), A323, A113C (offices); occupancysim `room_roles` overridden so only ours are lecture rooms on level 0 | Random rooms; all five of one type | The demo needs a guaranteed lecture fill at a known time; with ~50 lecture-sized rooms on level 0, occupancysim would otherwise scatter the lecture. Mixed roles also give the controller genuinely different regimes to handle. | We modify the input of a course tool — must be stated in the report as a scenario choice, not hidden. |
| D-12 | Physics as one container | One `physics` process for all rooms | One physics process per room | The rooms share one clock and one outdoor temperature; splitting them would fake independence the model does not have and multiply BuildSim polling. It is the *truth layer*, which by definition is not a distributed concern. | `physics` is a single point of failure for the simulation (not for the control system) — acceptable, and stated. |
